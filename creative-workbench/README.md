# 中华食肆 · 厨房工作台

本地工作版 0.4.2，面向团队自己的本机厨房；不是最终比赛交付。只做创意工作台，不涉及 Jacky 的生产工作台，也未制作“做同款”分发入口。

## 百味图 · 70 道游戏菜品（独立分支）

新增游戏 beta 0.6 的 70 道成品菜与原作故事。进入百味图即可浏览全部灰色菜品；确认完成制作后，同一道菜点亮，详情保留每次成品照、评分、日期和食忆，重复做不重复增加点亮数。样例与真实厨房分别计数。

21 道插画自带容器，49 道叠加游戏默认通用盘子；不是新生成的图片。素材在独立的 `assets/baiwei/`，不修改原材料卡片或厨房库存美术。来源与逐图哈希见 `docs/baiwei-provenance.json` 和 `lib/baiwei-dishes.json`。

**70 道图鉴已全部配备预设家常做法。** 从百味图或推荐点开菜品即可看步骤，无须请求模型。共 456 个步骤，每步写出用料、用量、火候、预计分钟数与完成判断；跟做时可按本步时长启动提醒。做法数据在 `lib/home-recipes.json`，所有菜品都有中文原作者页面、署名、支持范围与改编说明，完整索引见 [70 道中文做法来源](docs/CHINESE-RECIPE-SOURCES.md)。

每道菜标注实际基础人数与产出，不再把整鸡或两碗面称为一人份。每步分钟数是家庭操作估计，包含明确列出的泡发、腌制和等待，并非原作者实测或平台已实做。开做前确认备齐用料，再勾选“我已核对食材、到期信息与过敏原，确认具备所需厨具”，不再填写审校姓名或记录人工审校；游戏故事与菜谱来源分别标注。

### 本餐确认拥有，不必先录进冰箱

菜谱用料不足时，右侧显示红色 **确认拥有**，点击后变为绿色 **已拥有**，再次点击可取消。已有精确库存足量的食材直接显示已拥有。全部备齐并勾选原有核对项后，即可开始做。

- 只确认本餐差额：需 2 个鸡蛋、冰箱已有 1 个，临时确认另外 1 个；不新增候选或库存批次，也不影响推荐。
- 开做前关闭详情、重开、换菜或切厨房会清空确认；相关库存、到期状态或做法版本变化后需重新核对。开做后仅把本餐差额和原库存用量保存到烹饪记录，刷新或保存复盘草稿不会丢失。
- 完成时自动处理原有库存部分；临时部分不入库、不再扣库。开做后的新批次不会被自动选中，同批次补货也只减去开做时分配的用量，不要求用户再核对剩余量。
- 未知数量、不同单位、过期批次不会因此变成精确可用库存，也不改旧记录。临时确认不是对过期食材的食用许可；仍需核对实物、过敏原与所需厨具。

菜谱版本为 `2026-09-06-home.1`。新开餐使用新版；已保存的快照、旧版未带快照的三道菜会话继续使用原配方与份量。旧审校记录仅作历史数据保留，不再作为开做前置条件；做法更新后需重新勾选本餐确认。现有库存不迁移、不重写；新识别词典区分干湿、去骨/带骨和生熟材料，不按同一重量自动互换。

本分支独立预览不迁移原入口的浏览器数据，也不替换正在运行的厨房；合并升级时应继续沿用原入口。检查：`npm test`、`npm run typecheck`、`npm run build`、`npm run build:html`，然后运行 `node scripts/verify-baiwei-assets.mjs --html` 校验全部 71 个素材在独立 HTML 内完整嵌入。旧版本 ZIP 未覆盖。

## 可选：WorkBuddy 另写一版做法

1. 使用原入口 **http://127.0.0.1:43117/**；更新包后停止旧连接再启动新版，不改地址、工作目录或清空库存。
2. 在推荐菜上点 **跟着做这道菜**只会立即打开预设做法。需要另外生成时，在详情展开 **可选：请 WorkBuddy 另写一版做法**，再点生成按钮。网页仅发送该菜名字、基础人数与计划用料，不传整份冰箱、成品照或历史记录。
3. 在你自己的 WorkBuddy 对话加载本包新版 `skills/zhonghua-shisi/SKILL.md`，说 **“读取厨房任务，生成做菜步骤”**。沿用照片交接：Skill 读取本机任务，由当前 WorkBuddy 对话生成做法并提交回来；不用复制菜名、食材、prompt 或 JSON。
4. 页面自动接收步骤。核对做法后开始跟做；这一餐固定保存当时的版本，不会被后续重新生成覆盖。最后拍成品照（可选）、评分、写评论（可选），点击完成收录百味图。

这条新做法通道不下载或启动本地菜谱模型，不调用外部 AI API，不读取账号凭据；使用的是用户已登录的 WorkBuddy 对话能力与其网络/额度。本地脚本只传数据，不能主动唤醒 WorkBuddy，步骤 3 仍需用户发一句话。原有语音通道未改动，见下节。

仅显式点击生成按钮才准备任务；已经收到做法时直接查看，需要新版本可点“请 WorkBuddy 重新生成”。任务可取消；关闭详情不等于取消。没有连接不影响预设做法。照片与做法分开排队，正式库存仍只在页面确认后更新。

推荐从 70 道预设菜中按库存挑选，最多显示三道。WorkBuddy 是额外做法通道，基础配方来源不代表生成步骤已逐项查证，返回内容仍是待核对草稿，也不借用预设步骤的计时或材料标签。自动化使用标注的步骤夹具验证传输/持久化；真实 WorkBuddy 生成仍需实机验收。

## 公网语音录入（云端接口已实现，待配置服务凭证验收）

HTTPS 网页中的麦克风使用腾讯云一句话识别；普通用户不用安装本地模型、Python 或 WorkBuddy，也不用配置 API Key。浏览器录音转换为真正的 16 kHz 单声道 WAV，由工作台服务端签名请求，转写后继续使用原有食材候选与确认入库事务。语音不可用时可直接输入文字，不恢复 JSON 导入。

服务端凭证、D1 持久化限额、隐私边界与上线验收见 [云端语音配置](docs/CLOUD-VOICE.md)。默认每天全站 100 次尝试；没有配置好时明确显示未开通，绝不模拟成功。本轮未配置云凭证，尚未进行真实腾讯云/手机录音验收。

旧的 `127.0.0.1:43117` 入口仍保留已安装的本地语音服务，不会自动调用新云接口；单文件 HTML 没有服务端，云语音须使用部署后的 HTTPS 页面。原库存与 WorkBuddy 照片连接保持不变，未删除本机现有模型。

## 旧本地语音方案（兼容保留）

用户已明确允许语音由 WorkBuddy 或其他 AI 处理。本版选择**本机 Whisper 语音模型**，不等待 WorkBuddy 开放平台，不需要 API Key。保留全部旧库存、调料清单与 WorkBuddy 照片连接；不恢复 JSON 导入界面。

### 本地入口的语音录入

当前开发电脑已准备好语音环境。打开原入口 **http://127.0.0.1:43117/** → 我的厨房 → **语音录入** → 开始录音 → 允许麦克风 → 说完了，识别食材 → 核对清单 → **确认入库**。不切应用，不复制文字或 JSON。

- Whisper base（faster-whisper 1.2.1 / CPU int8）将录音转成简体中文，食材词典与数量规则整理成可编辑清单；不是用大语言模型自由编造库存。
- 最长录音一分钟、3 MB；结束、取消、关闭或切换厨房会释放麦克风，取消后旧响应不能入库。录音只在本机进程内存中处理，不保存音频文件，也不发送第三方；首次模型下载需要网络，准备好后转写使用本地模型。
- “一盒鸡蛋”按 1 盒，不猜枚数；斤按 500 克换算并提示。未知数量可明确确认“有，数量待确认”，不会冒充足够做菜。否定 / 计划购买不当库存；数量范围、改口、重复提及留待核对。有限词典可能遗漏生僻食材，页面会提示修改文字或手动补充。
- 可取消勾选，修改数量形式、数量 / 单位和到期日期；名字识别有误可改转写文字后重新识别。盘点自动关联唯一同名库存并保留日期，原话没说数量时保留已知数量。有多份同名库存时先取消该项，从各库存卡片“校准余量”；不猜测目标，也不自动合并。补货新增独立记录。
- 点击一次确认，所选条目在同一 IndexedDB 事务入库；失败整批回滚。草稿期间库存变化会要求重新核对，重试同一确认不重复添加。

其他电脑首次使用完整包时，需要 macOS、Node.js 22+ 和 uv。双击 **初始化语音.command**（或者源码中 `npm run voice:setup`），下载 Python 依赖及语音模型到完整包的 `.kitchen-voice/`；然后启动厨房。初始化脚本不会读取你的照片或库存。模型和虚拟环境不放进 ZIP / Git；本版不是无需准备即可在任何手机运行的云语音服务。

只双击 HTML 不含语音后端；云语音须使用部署后的 HTTPS 网站，本地 Whisper 仍使用原本地连接入口。不要换地址、清库存来升级。此前本地模型测试使用明确标注的合成普通话音频，不冒充用户麦克风实测，也不代表云端验收。

## 第一次使用：先勾选调料

新建的真实厨房会先显示调料清单。常用 8 项（食用油、盐、白糖、醋、生抽、老抽、料酒、淀粉），另有可展开的 6 种酱料 / 风味油、4 种鲜香配料与 12 种香料。默认不勾选未知库存；可以逐项选择，也可以主动点“选中常用项”，再取消家里没有的。

- 点击“确认加入”才在同一次 IndexedDB 事务中写入所选调料和完成标记；勾选、展开、关闭不写库存。
- 只记录“有，数量待确认”，不假定克数、毫升数、到期日期或“充足”。推荐可以展示使用这些调料的菜，但仍提示核对所需用量；校准前不会解锁“食材已齐”或自动扣减。
- 已有且未过期 / 未耗尽的调料显示“已记录”，不会重复添加，也不改旧批次数量、日期或 revision。只有过期 / 已用完的旧批次时，明确勾选会新增记录，旧批次保留。
- 可以“暂时跳过”，以后在“我的厨房 → 调料清单”补选。已有厨房也可使用此入口，不会被强制重新 onboarding；未勾选不等于删除旧库存。
- 鸡蛋、番茄、肉类、米饭等其他食材可用网页语音或 WorkBuddy 照片录入；保留手动补充作为备用。不自动给用户添加食材或饮用水。

无需清空现有库存体验新版；使用原本的本地入口和 release 工作台目录，保持同一个 workspaceId。

照片留在 WorkBuddy 对话中；连接只传递食材候选，不读取模型密钥或正式库存，不调用开放平台 API。连接只监听本机，不能将这个 localhost 链接发给别人或直接在另一台手机上使用。未来复用者也须在自己的 WorkBuddy 上传照片并运行自己的本地包，不共用你的数据或账号。

注意：本地连接入口与旧的 file:// HTML、开发预览是不同浏览器来源，**旧库存仍在旧页面，不会自动迁移**。请保留旧页面与备份；本版没有整库恢复 UI。不要把备份作为食材候选导入。

## 真实厨房

- 网页语音清单 → 批量确认；手动表单 / WorkBuddy 自动交回 → 候选 → 数量形式、数量、到期日期 → 确认。手动补充与拍照识别同为边框按钮，调料清单为轻量文字入口。
- 默认盘点校准，补货新增。库存卡片的“校准余量”自动记住对应记录，不需选择批次。盘点不删除未看到的食材。
- 游戏百味图中的 47 种食材和 16 种调料均使用大白菜库存卡模板；蔬食、荤食、调料沿用各自原卡框，卡内只展示校准状态、现实数量和到期日。
- “盒、袋”不自动换算；数量档仍可记入库存，但不足以证明菜谱要求的精确数量。可回厨房盘点，或在菜谱里仅确认本餐用料，不改库存。
- 食材、油、盐、饮用水仍需确认，不默认添加。已移除用餐设置区，默认厨具齐备；只按确认库存的覆盖率与临期情况排序，最多三个推荐。旧版保存的人数、时间、厨具、过敏与忌口字段不再作为隐藏筛选。新开餐使用菜谱标注的基础份量，已有会话保留原份量；菜谱提示不代表对任何食物过敏情况作安全保证。
- 70 道基础做法为有中文来源的家庭改写；可选用自己的 WorkBuddy 另写步骤。开做前保留一个食材/到期信息/过敏原/厨具确认勾选，删除独立审校表单及后台审校门槛。仍检查每项库存足量或本餐差额已确认、当前菜谱版本和是否已有进行中的一餐；不伪造或自动填入审校记录。
- 步骤、暂停、提醒截止时间会保留；复盘只呈现成品照、评分和评论，可“保存草稿”。点击完成才自动按开做时菜谱计划处理库存，不会边做边扣库存。
- 成品照可跳过；本地压缩保存，不上传。评分分为好吃程度、制作难度、卖相程度，三项均为本人选择的 1–5 星；难度 1 星困难、5 星简单，不与另两项合并成总分。三项都填写后可完成；未填完可保存草稿。此前按相反方向填写的三维难度，在展示或恢复草稿时按 `6 - 原分数` 换算，新评分携带方向标记以免重复翻转；原记录不批量重写。
- 百味图、做菜历史与单条导出保留三项分数；旧记录显示“旧版评分”，不会据此猜测好吃、难度或卖相。旧草稿的照片和评论保留，新的三项需分别选择。不用 AI 猜味道或安全性。
- “完整备份”导出当前厨房的私人状态，包括照片，请保管好。首版尚未开放整库备份恢复 UI；不要将备份当作食材识别结果交回。

## 数据与事务

唯一真源：IndexedDB，独立 HTML 的数据库名为 zhonghua-shisi-kitchen-v1；本地连接模式额外附带完整包的 workspaceId，以免同一端口使用另一份工作台时混用。inventory、candidates、sessions、meta 四个 object store，每个以 real / demo 分区。写操作在同一个覆盖四个 store 的 readwrite 事务中提交；不向 CSV、localStorage 或服务器双写库存。

连接队列不是第二份库存：未接收候选及待生成/待接收做法暂存于完整包的 .kitchen-bridge/queue.json；网页事务成功后回执并清除候选正文或做法/用料正文。localStorage 只存浏览器投递身份。每个 ticket 固定厨房、方式和幂等 ID，取消/过期不跨轮复用；清空厨房同时取消相应投递并保存忽略标记，避免旧请求回流。整个 .kitchen-bridge/ 是私人运行数据，不进入 ZIP 或 Git。

- 候选决策以 requestId + candidateId 去重，拒绝/确认结果保留。
- 库存更新要求批次 revision 匹配。
- 烹饪完成以 session.id 去重，库存变化与完成记录在同一事务提交；失败全部回滚。所有新会话保存开做时的原库存分配，完成时按当前同批次扣减、不小于零、不改扣新增批次。删除、换身份/单位或变为模糊数量的记录保持原样；旧会话从自己的库存快照和开做日期回退，不读取旧草稿的手动消耗清单。自动完成标记 `consumptionMode: recipe-plan`，表示按配方记账而非用户实测消耗。
- 百味图由已完成会话派生，同菜重复完成只增加历史。
- 单份百味图导出只含选中的完成记录、对应菜品文案与来源，不含整份库存；个人文字转义后输出。
- 图片、自由文字、文件均是输入数据，不能作为直接改库存的指令或确认凭据。
- 同浏览器来源共享本地存储，不是登录账号隔离。换浏览器 / origin / 文件路径可能不是同一存储上下文。无跨设备同步，无云账号。

## 开发与构建

Node 22.14 已用于本次验证。保留 Sites/Vinext + React + shadcn 项目结构；独立 HTML 由同一 App 源码构建，不维护另一套业务逻辑。

```sh
npm install
npm run dev -- --host 127.0.0.1 --port 5177
npm run typecheck
npm test
npm run build
npm run build:html
npm run package:local
npm run kitchen:start
npm run kitchen:status
npm run kitchen:stop
npm run voice:setup
npx tsx scripts/verify-voice-live.ts
```

第一份是正常 Web 构建；第二份把 React、界面、70 道菜谱、菜品插画、库存卡和通用盘子内嵌进 release/中华食肆.html，不依赖 CDN、远程字体或 API Key。预设做法可离线查看，打开外部参考链接需联网。不要把开发工具链的 node_modules 装进 WorkBuddy。

skills/zhonghua-shisi/SKILL.md 为可携带的“中华食肆 Skill”，包含本地交接脚本、候选协议和 70 道菜的主题资产说明。脚本不依赖 npm 包，只需 Node.js。请在实际 WorkBuddy 中按其支持的方式导入/加载。这里只生成文件，未自动安装，也未验证模板市场格式。

照片或核对文字 → Skill 提取并自动提交 → HTML 自动接收候选 → 人工确认。对话仍不知道网页最新库存；需要对话分析库存时，由用户主动分享自己导出的数据。脚本 start 启动本地后台连接，stop 只停止连接，不删除库存；更新包后应停止旧连接再启动新版。
